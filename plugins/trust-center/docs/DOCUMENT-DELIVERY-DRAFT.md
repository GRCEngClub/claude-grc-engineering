# Draft: version-pinned document delivery and revocation

**Design proposal, not an approved architecture or deployment instructions.** Deployment, seeding, sensitive-data use and all downloads remain disabled. The maintainer must choose the hosting/access model; #148 is not resolved. No AWS resources or end-to-end verification were available. This proposal addresses AWS only and does not implement NDA enforcement.

## Proposed boundary and contract

Use an authenticated application delivery service as the *only* private-document read path. It verifies the identity supplied by a correctly configured API Gateway Cognito authorizer, checks current authorization against authoritative DynamoDB base-table records, then reads the exact approved S3 object version and returns bytes. The client never receives S3 credentials, an S3 URL, or a reusable download capability. Public and private documents use separate namespaces/buckets and delivery policies; a public object/version must never become private in place. Publicly disclosed bytes are irretrievable even after removal. A formerly public document made private requires a new private key, version and generation; do not copy old approvals. Admin access must be an explicit separately reviewed policy, not an unchecked bypass.

The proposed revocation guarantee is **authorization at admission**, not instantaneous cessation of disclosure: after a committed revocation, subsequently admitted requests using an authoritative transactional snapshot must fail. A request admitted before the commit can start or complete delivery afterward. An already downloaded copy, already sent bytes, or a client-held connection cannot be recalled. If the product requires stopping active transfers or zero bytes after a revocation acknowledgement, this design is insufficient; define an implementable stream-cancellation protocol, failure semantics and independent tests, or do not launch. Do not call bounded presigned URL expiry immediate revocation.

## Publish, approve, deliver, revoke

1. A separately authorized publisher uploads to a private, versioning-enabled general-purpose bucket under a new unpredictable, never-reused key for each incarnation. Verify the bucket has versioning **Enabled**, not suspended, and capture the non-null S3 `VersionId`, content length, cryptographic SHA-256 and media type from the controlled ingestion pipeline. Scan and validate content before publication. Versioning preserves versions but is not WORM: privileged deletion and lifecycle rules can remove versions. Consider Object Lock and retention/legal-hold requirements separately, including their effects on deletion and cost. Object Lock protects individual versions, not new versions at the same key. Store bucket, key, exact version ID, digest, size, classification and fresh random generation in the authoritative document record; never accept these fields from a download request. Reject absent or `null` versions. A verified upload may be orphaned on failed publication; cleanup must not delete referenced versions.
2. Atomically publish or replace the document record with a fresh generation using conditional writes. Bind each approval to trusted issuer and subject (or one pinned user pool and subject), document ID and generation. Existing prototype regenerates generation on every save; keep that fail-closed behavior unless changed under review. Replacement, deletion or visibility change must invalidate approvals, including stale admin decisions. Use versioned conditional decision updates and document-generation checks; no migration of legacy approvals without independent verification.
3. For each GET, Gateway authenticates; the handler fails closed on missing or invalid authorizer context. Resolve identity from verified claims and validate route and document ID. Strongly read the base document to derive its generation-dependent canonical decision key, then use a DynamoDB `TransactGetItems` of the document and that decision (or an equivalent proven serializable snapshot). Reject or restart if the transaction's document generation differs from the preliminary read; do not authorize based on the preliminary read. Check active state, exact generation and approved status; do not use a GSI, stale cache, client-supplied key, identity, version or status. Explicitly authorize admins under a reviewed rule. Deny uniformly on missing, deleted, inconsistent, legacy, or unavailable state; fail closed on transaction/read errors. Authenticate again on each new request, including Range/retry requests. Record admission using a privacy-preserving audit identifier; no bearer tokens, URLs, document content or secrets in logs.
4. After admission, service calls S3 `GetObject` with the server-stored bucket/key/**VersionId**; verify the returned version and expected length, fail closed on S3 errors and do not silently fall back to the current version. Return safe `Content-Type`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`; disable CDN/API caches for the route and errors. SHA-256 is verified during ingestion and should be checked before release if the delivery path can buffer safely; streaming cannot retract bytes if an end-of-stream digest mismatch is discovered. Document and test the chosen integrity boundary. Enforce a reviewed maximum size before fetching, and define Range/retry and partial-response semantics.
5. Revocation/denial conditionally updates the canonical decision in the same authoritative region; deletion/replacement invalidates the document generation. Acknowledge only after the write commits; a transactional read ordered after that commit must deny. Concurrent reads/writes may serialize in either order: a transaction that admits first remains admitted even if it responds after revocation. DynamoDB and S3 are not one transaction; neither a second read nor an S3 fetch closes the final check-to-send race. Strong single-item reads alone do not yield a cross-item atomic snapshot. Do not rely on eventually consistent GSIs, TTL deletion or asynchronous replicas for revocation. Availability failure must deny, not fall back. The contract applies to one authoritative region; multi-region operation requires a separately proved consistency/failover design.

## AWS and IAM constraints

- `GetObject` with a version ID requires `s3:GetObjectVersion`; unversioned current-object reads use `s3:GetObject` instead ([API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)). Grant the delivery role only required versioned reads on the private document prefix, DynamoDB reads on required tables, logging and, if SSE-KMS is used, narrowly scoped `kms:Decrypt` with a compatible key policy. Separate publisher, administrator and delivery roles; delivery must not write, delete versions, change policy or issue presigned URLs. IAM permission to read also permits code holding that role's credentials to generate a presigned request: forbidding URLs is an application/trust-boundary requirement, not an IAM action named “presign.” Protect credentials and invocation paths; test effective permissions, bucket policies, KMS grants, SCPs and explicit denies. S3 Block Public Access, bucket-owner-enforced ownership and TLS-only access are prerequisites, not substitutes for authorization.
- A normal S3 delete creates a delete marker; a version-specific GET can still retrieve an older version. A version delete or an explicit policy/credential deny can block access, but cannot retract a completed or in-flight transfer, and Object Lock may prevent deletion ([versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html), [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). Do not treat a delete marker as revocation of pinned versions.
- API Gateway REST API buffered payload limit is 10 MB; synchronous buffered Lambda request/response limit is 6 MB including the encoded response envelope. Binary proxy responses require base64, further reducing usable file size; establish and test a conservative application limit rather than assuming 6 or 10 MB of file bytes ([REST quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-execution-service-limits-table.html), [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html), [binary proxy](https://docs.aws.amazon.com/apigateway/latest/developerguide/lambda-proxy-binary-media.html)). If larger documents are required, choose and validate a compatible authenticated streaming service/integration, timeouts, range behavior and limits separately; do not assume the existing REST deployment supports it. Lambda streaming's 200 MB quota alone does not prove Gateway integration compatibility.
- The present REST API has an unauthenticated greedy proxy and trusts gateway claims; deny direct untrusted Lambda invocation, function URLs and alternate event sources. Explicitly map and test each method/path, including greedy fallback, encoded paths, OPTIONS, missing/invalid tokens, authorizer issuer/audience/token type, admin membership and the deployed stage. Lambda resource policy `SourceArn` must be scoped to intended API/stage/methods; execution-role permissions are a separate boundary. Disable API caching, prevent CloudFront API error rewrites and ensure no alternate origin bypass. Validate browser CORS and token handling. Do not assume template configuration demonstrates effective routing.
- An alternative short-lived S3 presigned URL is a reusable bearer capability until expiration or earlier credential/policy denial. S3 checks expiry at request start, so an already started transfer can continue; temporary credentials can shorten lifetime, and `s3:signatureAge` can cap signature age ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)). A version-pinned URL prevents later key overwrites from changing its bytes, but app-level revoke does not invalidate it, and anyone holding it can replay/share it. It is unsuitable for the proposed per-request admission boundary. Existing old URLs may be unpinned and need separate incident assessment.
