# Document access security and remaining work

**Deployment is blocked for all data, including synthetic data. Never deploy or handle sensitive data.** Both deployment scripts exit nonzero, seeding is blocked, and both CloudFormation templates include a deliberately false rule. These are accidental-use guardrails, not protection for previously deployed or modified copies; no AWS deployment has verified the CloudFormation rule. Do not bypass them. Re-enable only after the hosting/access model is selected, blockers are resolved, and independent end-to-end security review is complete.

The public API returns only explicitly public documents. Private document details require a Cognito-authorized `/api/private/documents/...` route and an approval bound to the caller's exact Cognito subject and document incarnation; admins can also access private metadata. All new signed download URLs are disabled, including public URLs and admin requests. This assumes a single trusted Cognito user pool and verified gateway authorizer; a multi-issuer design must also bind the issuer. Email is not an authorization identity.

This remains incomplete groundwork, not a usable production access flow. A requester prototype provides provisioned-account sign-in, explicit refresh of public and approved metadata, and requests by an out-of-band document ID. It has not been tested with a real identity provider or gateway. Clients and handlers accept only 1–128 ASCII letters, digits, hyphen and underscore. Legacy unsafe IDs are hidden and cannot be accessed or decided; securely re-register under new IDs and obtain fresh approvals, never migrate existing approvals. Request status and approved downloads are not implemented. Cognito sessions refresh on demand in memory; reload or full-page navigation requires signing in again. Unsupported Cognito authentication challenges, account provisioning, recovery, MFA, secure session storage and XSS protections need design and testing. Authorization is always enforced server-side, never by this UI. The API base is configuration-controlled; never point it at an untrusted origin, since it receives bearer tokens. Browser no-store requests do not establish gateway/CDN caching policy. Demo mode is opt-in with `VITE_DEMO_MODE=true` even when an API URL is configured; it uses fictional data, does not contact the API, and admin decisions are simulated locally. Demo requests and downloads do not succeed. Previously issued presigned links can remain usable until expiry or earlier denial by credentials, policy, or object changes, including after application-level revocation or a public-to-private change. Previously disclosed objects and metadata cannot be recalled. An approval does not enforce NDA signing.

The handler trusts API Gateway authorizer claims on private/admin paths. Never expose the Lambda through an unauthenticated function URL or permit untrusted direct invocation. API Gateway routing, Cognito token/claim behavior, CloudFront caching and forwarding, S3 bucket isolation, permissions, deployment replacement, CORS, and end-to-end access have not been validated in AWS. CloudFormation API Gateway deployments may need replacement on updates; verify the deployed stage includes all methods. The reference infrastructure is synchronized with the main template, but neither has been validated in AWS. Do not deploy without resolving these items and reviewing the complete security configuration.

CloudFront custom error responses currently rewrite 403/404 responses to the SPA with status 200, including API errors; separate SPA fallback from API error handling before deployment. The CloudFormation Lambda contains placeholder code and must be replaced by the real handler as part of a verified deployment. The API stage deployment must be replaced when methods change. Private document requests require an out-of-band document ID because undisclosed documents are absent from the public list; design a non-disclosing request/discovery flow before enabling it.

The request endpoint distinguishes unknown, public, existing and legacy IDs in HTTP responses to authenticated callers; the generic UI error does not fix that API-level enumeration oracle. Decide whether catalog existence is sensitive, then design and test uniform responses, rate limits, abuse handling and request lifecycle controls at the server and edge before enabling access. Document IDs are not secrets or authorization. Input length limits in this prototype are not server-side validation.

A [draft AWS document-delivery and revocation design](DOCUMENT-DELIVERY-DRAFT.md) proposes a boundary and validation gates; it is unapproved and does not enable deployment or downloads.

## Authorization lifecycle and migration

Every document save, including an unchanged save or a public/private transition, assigns a fresh random generation. Deletion and recreation, even with the same ID, cannot reuse the old authorization incarnation. A single canonical request key is derived from the unambiguously encoded generation and exact subject; conditional creation rejects concurrent or subsequent duplicate requests with 409. Its pending/approved/denied status is the sole authorization decision. An admin can explicitly change denied back to approved; repeat requests do not reset a decision. Every decision requires the version observed by the administrator; a conditional update changes that version on every transition and returns 409 on conflict. This prevents stale and ABA decisions, including an old approval racing a denial. Request list results come from an eventually consistent GSI, so stale versions must be refreshed and can still conflict. Legacy requests lacking versions cannot be decided; create fresh requests rather than assigning versions to old approvals. The decision transaction condition-checks the current document generation and ID atomically with the version-guarded request update. A concurrent deletion or save before the transaction commits prevents the decision; a later save revokes that generation. Old request records are ignored, not consulted as fallback.

Legacy documents without a generation fail closed for non-admin private access and new requests; legacy requests cannot be approved through the new endpoint. Re-register document metadata and obtain fresh authenticated requests and approvals. There is no automatic migration; any proposed migration needs independent identity and document-incarnation verification and a reviewed, fail-closed procedure. Do not copy old approvals blindly. Admin access is separate and remains available for administration.

Strongly consistent reads do not make the document read, decision read, and S3 signing atomic. Signing is therefore unconditionally disabled for all documents: disabling only gated signing would not protect a formerly public S3 key reused for private data. There is no flag to re-enable signing. A public URL issued before this change may read a later object at the same mutable S3 key, including a new document incarnation. Existing deployments and old URLs are not fixed by this code; operators must assess and revoke them via AWS credentials, bucket policies, and object/key handling. No in-flight request handled by this version issues a link: signing is disabled. Earlier code or another deployment may still issue links, including during a revocation race. Previously issued presigned URLs are bearer capabilities: application revocation, deletion, and changing visibility do not invalidate them; they can remain usable until their configured expiry (or until underlying credentials/policy/object deny access). Already downloaded data cannot be recalled. Strict immediate revocation requires a different, validated delivery architecture and concurrency model. Neither AWS end-to-end behavior nor non-AWS hosting has been demonstrated; the maintainer's choice of hosting target and private-access model remains open.

Admin request listing returns at most 50 evaluated records per call. Pass the returned `nextCursor` as the URL-encoded `cursor` query parameter with the same optional `status` filter until it is null. Cursors are opaque but not signed; only admins can use this endpoint. The dashboard loads further pages on demand and resets to the first page after decisions. GSI results are eventually consistent and not a snapshot; pagination can miss or duplicate concurrently changing records. This is not an authoritative audit/export API. Document listing evaluates at most 50 records in one query and returns 503 rather than silently omitting results if DynamoDB reports another page (including its 1 MB page limit); full catalog pagination remains unimplemented. The activity log is best-effort: writes can fail without failing the operation, so it is not an authoritative audit trail. Transaction conflicts return a retryable 409; refresh the request before retrying. No AWS end-to-end testing has been performed.

Metadata authorization reads are not atomic with responding: an in-flight metadata read can return a previously authorized snapshot after a denial, document replacement, or deletion. Revocation is not immediate for in-flight responses; previously disclosed metadata cannot be recalled.
