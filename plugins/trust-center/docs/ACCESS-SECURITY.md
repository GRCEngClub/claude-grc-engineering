# Document access security and remaining work

**Deployment is blocked for all data, including synthetic data. Never deploy or handle sensitive data.** Both deployment scripts exit nonzero, seeding is blocked, and both CloudFormation templates include a deliberately false rule. These are accidental-use guardrails, not protection for previously deployed or modified copies; no AWS deployment has verified the CloudFormation rule. Do not bypass them. Re-enable only after the hosting/access model is selected, blockers are resolved, and independent end-to-end security review is complete.

The public API returns only explicitly public documents. Private document details require a Cognito-authorized `/api/private/documents/...` route and an approval bound to the caller's exact Cognito subject and document incarnation; admins can also access private metadata. All new signed download URLs are disabled, including public URLs and admin requests. This assumes a single trusted Cognito user pool and verified gateway authorizer; a multi-issuer design must also bind the issuer. Email is not an authorization identity.

This is backend groundwork, not a complete user-facing access flow. The frontend defaults to same-origin public data and does not support downloads, but does not implement requester sign-in, private document discovery, requests, or approved downloads. Demo mode is opt-in with `VITE_DEMO_MODE=true` even when an API URL is configured; it uses fictional data, does not contact the API, and admin decisions are simulated locally. Demo requests and downloads do not succeed. Existing presigned links remain valid until their one-hour expiry, including after revocation or a public-to-private change. Previously disclosed objects and metadata cannot be recalled. An approval does not enforce NDA signing.

The handler trusts API Gateway authorizer claims on private/admin paths. Never expose the Lambda through an unauthenticated function URL or permit untrusted direct invocation. API Gateway routing, Cognito token/claim behavior, CloudFront caching and forwarding, S3 bucket isolation, permissions, deployment replacement, CORS, and end-to-end access have not been validated in AWS. CloudFormation API Gateway deployments may need replacement on updates; verify the deployed stage includes all methods. The reference infrastructure is synchronized with the main template, but neither has been validated in AWS. Do not deploy without resolving these items and reviewing the complete security configuration.

CloudFront custom error responses currently rewrite 403/404 responses to the SPA with status 200, including API errors; separate SPA fallback from API error handling before deployment. The CloudFormation Lambda contains placeholder code and must be replaced by the real handler as part of a verified deployment. The API stage deployment must be replaced when methods change. Private document requests require an out-of-band document ID because undisclosed documents are absent from the public list; design a non-disclosing request/discovery flow before enabling it.

## Authorization lifecycle and migration

Every document save, including an unchanged save or a public/private transition, assigns a fresh random generation. Deletion and recreation, even with the same ID, cannot reuse the old authorization incarnation. A single canonical request key is derived from the unambiguously encoded generation and exact subject; conditional creation rejects concurrent or subsequent duplicate requests with 409. Its pending/approved/denied status is the sole authorization decision. An admin can explicitly change denied back to approved; repeat requests do not reset a decision. Every decision requires the version observed by the administrator; a conditional update changes that version on every transition and returns 409 on conflict. This prevents stale and ABA decisions, including an old approval racing a denial. Request list results come from an eventually consistent GSI, so stale versions must be refreshed and can still conflict. Legacy requests lacking versions cannot be decided; create fresh requests rather than assigning versions to old approvals. The document generation read and decision update are not transactional: a concurrent document deletion or save can leave an obsolete decision, which must not authorize a new generation. Old request records are ignored, not consulted as fallback.

Legacy documents without a generation fail closed for non-admin private access and new requests; legacy requests cannot be approved through the new endpoint. Re-register document metadata and obtain fresh authenticated requests and approvals. There is no automatic migration; any proposed migration needs independent identity and document-incarnation verification and a reviewed, fail-closed procedure. Do not copy old approvals blindly. Admin access is separate and remains available for administration.

Strongly consistent reads do not make the document read, decision read, and S3 signing atomic. Signing is therefore unconditionally disabled for all documents: disabling only gated signing would not protect a formerly public S3 key reused for private data. There is no flag to re-enable signing. A public URL issued before this change may read a later object at the same mutable S3 key, including a new document incarnation. Existing deployments and old URLs are not fixed by this code; operators must assess and revoke them via AWS credentials, bucket policies, and object/key handling. An in-flight request can race a denial, document change, or deletion and issue a link after that change. Previously issued presigned URLs are bearer capabilities: application revocation, deletion, and changing visibility do not invalidate them; they can remain usable for up to one hour (or until underlying credentials/policy/object deny access). Already downloaded data cannot be recalled. Strict immediate revocation requires a different, validated delivery architecture and concurrency model. Neither AWS end-to-end behavior nor non-AWS hosting has been demonstrated; the maintainer's choice of hosting target and private-access model remains open.

Request listing exhausts DynamoDB query pages in one response; large datasets may exceed Lambda time/memory or response limits. GSI results are eventually consistent and not a snapshot; pagination can miss or duplicate concurrently changing records. This is not a scalable or authoritative audit/export API. No AWS end-to-end testing has been performed.
